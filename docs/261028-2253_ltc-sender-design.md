# LTC 送出ツール (LtcSender) 設計案

**作成日**: 2026-10-28
**状態**: 設計確定 (未実装)。次は実装計画 (plan) に落とす

## 1. 目的

Ableton Live (12 Standard、セッションビューでのポン出し) を親にして、照明・映像へ LTC を送る。

- LTC は**音声ファイルとして Live のクリップで鳴らす** (Max for Live が無いため)。BGM と同じシーンに置き、BGM とサンプル単位で揃って鳴る
- ツールは、その LTC ファイルの**作成・配置の確認・本番中の監視・リハ用の途中再生**を受け持つ
- 本番でも使う。リハ専用の機能も、本番の安全を崩さない作りにする

LTC をツールがその場で作って出す方式 (ClipSMPTE 型) は採らない。2 つ目の音声出力が要り、フレーム精度の保証が難しいため。

## 2. 実機で確認済みの前提 (2026-10-28、Live 12 Standard、WATA-TP)

| 項目 | 結果 |
|---|---|
| LTC クリップの設定 | Warp オン・**Re-Pitch**・クリップ BPM = Set のテンポ (120)。録音して解読し、フレームの抜けなし、30 秒で 1ms 未満の誤差 |
| ファイル上の時刻と拍の関係 | 拍 = 秒 × テンポ ÷ 60 (Start 866 拍 = 433 秒 = LTC `01:07:13` で一致) |
| 再生中に飛ばす | `Clip.move_playing_pos(拍)` を 1 つの OSC バンドルで全クリップへ。揃って飛ぶ (位置の差 0)。送ってから 0.15〜0.37 秒。LTC は正しい時刻へ切り替わるが、切り替わりの瞬間に壊れたフレームが 1 つ出ることがある |
| 止まっているシーンを途中から始める | `scrub(拍)` と `stop_scrub()` を**同じバンドル**で全クリップへ。目的の位置から揃って鳴り、曲の頭は出ない。LTC も最初のフレームから目的の時刻 (サンプル単位で一致)。送ってから 0.3〜0.4 秒 |
| scrub だけ送った場合 | 目的の位置の約 0.1 拍を繰り返す (音が詰まる)。必ず stop_scrub を同じバンドルに入れる |
| 「再生待ち」のクリップ | `is_playing=False` / `is_triggered=True` のクリップには move_playing_pos がエラーなしで無視される |
| Warp オフのクリップ | move_playing_pos で飛ばせない (LOM の仕様) |
| Start を再生中に変える | 再生位置も変わってしまう (ユーザーの経験) ので、Start の書き換えは使わない |
| AbletonOSC | 上流 (ideoforms/AbletonOSC、最終 push 2025-11-19) には move_playing_pos / scrub / stop_scrub が無い。`abletonosc/clip.py` の `methods` に 3 行足すと使える (手元は追加済み、元は `clip.py.bak-20261028`) |

## 3. 全体の構成

```
[LtcSender (Node, 新パッケージ)] --OSC 11000--> [AbletonOSC (改造版)] --> Live
        ^                                              |
        |  11005 (osc-router が複製転送)                  | 11001
        +------------------ [osc-router] <-------------+
        |
        +-- HTTP/Socket.IO 3002 --> 操作画面 (ブラウザ)
        +-- HTTP API ------------> viewWaves から呼ぶ (波形クリック、第 2 段階)
```

- 置き場所: `packages/LtcSender`。`config.json` に `httpPort: 3002`、`oscPort: 11005` で追加し、`suite-launcher` から起動する
- 返信は osc-router が全パッケージに複製転送するので、viewWaves・DaihonTrigger と同じ受け方になる
- **注意**: AbletonOSC のリスナー (`start_listen`) は Live 側で 1 つしか持たない。LtcSender が `stop_listen` を送ると viewWaves の監視まで止まる。LtcSender は `stop_listen` を送らず、必要な値は `get` の定期取得か、viewWaves が張ったリスナーの返信をそのまま使う

## 4. 機能

### 4.1 台帳 (キューリスト)

シーンごとに次を持つ。保存先は `packages/LtcSender/project_data.json` (DaihonTrigger と同じ形)。プロジェクト (.als) ごとに切り替えられるようにする。

| 項目 | 例 |
|---|---|
| シーン番号 | 13 |
| BGM のトラック | `A ch` (番号ではなく名前で持つ。トラックの並べ替えに強くするため) |
| LTC のトラック | `LTC` |
| LTC の開始時刻 | `01:00:00:00` |
| フレームレート | 29.97DF (ショー全体で 1 つ) |
| LTC ファイル | 作成したファイルのパス |

### 4.2 LTC ファイルの作成

- Node で LTC を符号化して WAV に書く (48kHz、モノラル)。長さは BGM のファイル長 + 余白
- 符号化の細部 (立ち上がり時間、レベル、ユーザービット) は、実装前に SMPTE ST 12-1 の一次資料で確かめる
- 作ったファイルは、作成直後に自前の解読処理で読み戻し、開始時刻・フレームレート・連続性を検査してから「作成済み」にする

### 4.3 LTC クリップの配置

- **第 1 段階**: オペレーターが Live の LTC トラックへドラッグする。ツールは置かれたクリップを検査して結果を表示する (4.4 の検査項目)
- **第 2 段階 (要検証)**: `ClipSlot.create_audio_clip(path)` (LOM に記載あり) で自動配置する。読み込み時の自動ワープで BPM が勝手に推定される問題があるので、Warp と BPM を確実に揃える方法を実機で確かめてから採用する

### 4.4 本番中の監視

シーンが発音されたら、そのシーンについて次を確かめ、外れていれば画面全体を赤くして知らせる。

| 検査 | 合格の条件 |
|---|---|
| LTC が鳴っているか | BGM が鳴っているのに LTC のクリップが `is_playing=True` でない → 異常 |
| BGM と揃っているか | 2 つの `playing_position` の差が 0.002 拍 (1ms) 以内 |
| LTC の Warp | Warp オン・Re-Pitch |
| 時刻の対応 | LTC クリップの長さ (拍) ≒ ファイル長 (秒) × テンポ ÷ 60。ずれていればクリップ BPM がテンポと違う |
| LTC トラック | ミュートされていない・音量が基準値・出力が Master 以外 (専用出力) |
| Set の設定 | テンポが台帳の値 (120)・グローバルクオンタイズが None |

### 4.5 表示

- **今出ている LTC の時刻**を大きく表示する。LTC クリップの再生位置から計算する (時刻 = 開始時刻 + 拍 × 60 ÷ テンポ。ドロップフレームを考慮)
- 次のシーンの開始時刻、曲の残り時間

### 4.6 途中から再生・飛ばす (リハ用、本番でも非常時に使える)

| 操作 | 仕組み |
|---|---|
| 止まっているシーンを「1:23 から」 | シーン内の全クリップへ `scrub(拍)` + `stop_scrub()` を 1 バンドルで送る |
| 再生中に「1:23 へ」「±10 秒」 | シーン内の再生中の全クリップへ `move_playing_pos(差の拍)` を 1 バンドルで送る |
| 波形クリック (第 2 段階) | viewWaves の波形クリックから LtcSender の HTTP API を呼ぶ |

- 「シーン内の全クリップ」は、そのシーンで鳴る全トラック (BGM・LTC・A ch' など) を指す。1 つでも漏れると音とずれる
- 送る前の確認: 全クリップが Warp オン、再生中の場合は全クリップが `is_playing=True`
- 送った後の確認: 0.5 秒後に全クリップの位置を読み直し、揃っていなければ赤で警告する
- 秒と拍の換算には Live から読んだテンポを使う (決め打ちしない)

### 4.7 安全装置

- **モード**: 「本番」と「リハ」を画面上部に大きく表示する。途中再生・飛ばす操作は、本番モードでは確認を 1 回挟む (6. を参照)
- **プロジェクトを書き換えない**: 発音・スクラブ・飛ばすだけを使い、Start・ミュート・音量は操作しない。ツールが落ちても Live の状態は普通のポン出しのまま残る
- **AbletonOSC の改造の管理**: 改造版の `clip.py` の差分をリポジトリに入れ (AbletonOSC は MIT ライセンス)、導入スクリプトで当てる。起動時に、手元の `clip.py` に 3 つの命令があるかをファイルから確かめ、無ければ赤で知らせる。AbletonOSC を更新すると改造が消えるため

## 5. 段階

1. **第 1 段階**: 台帳・LTC ファイルの作成と検査・監視・時刻表示・途中再生 (時刻入力と ±)・AbletonOSC 改造の導入スクリプト
2. **第 2 段階**: LTC クリップの自動配置・viewWaves の波形クリック連携

## 6. 決めたこと (2026-10-28)

- **LTC の開始時刻**: 台帳でシーンごとに自由に指定する。「M1 = 01:00:00:00、M2 = 02:00:00:00 …」のような自動入力も用意する
- **操作画面**: LtcSender 専用の独立した画面にする。波形クリックだけ、第 2 段階で viewWaves から LtcSender の API を呼ぶ
- **本番モードでの途中再生・飛ばす操作**: 確認を 1 回挟んで許可する。リハモードでは確認なしで使える

## 7. 実装前に確かめること

- 照明卓・映像サーバーで、Re-Pitch の LTC と、飛ばした瞬間の壊れたフレーム 1 つの扱い
- LTC の出力レベル (今の録音でピーク -26 dBFS) を受け側が読めるか
- `create_audio_clip` で置いたクリップの Warp と BPM の決まり方 (第 2 段階のため)
