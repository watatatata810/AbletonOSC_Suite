# Ableton OSC通信輻輳制御およびバーストガード 設計仕様書

## 1. 目的と概要
再生中（Playing）にアプリを起動・再接続した際、AbletonOSC からの超高頻度の再生位置パケット（1秒あたり60発）によるネットワークおよびスレッドの輻輳（ふくそう）により、初期化に必要な `/num_tracks` への応答が約10秒間遅延し、さらに遅延したリクエストの重複応答（約20回連続）が一斉に届くことで、リスナー設定リクエストのバースト（雪崩現象）が発生して起動までに数十秒フリーズする問題を修正します。

以下の3つの手段で、OSC通信の輻輳制御とバーストガードを実装します：
1. **リクエスト再送制限（デバウンス）**: 初期化要求 `/num_tracks` の再送間隔を 0.5秒から 2.0秒に延長し、Ableton へのパケット滞留を防ぎます。
2. **重複応答ガード**: 一挙に届く重複した `/num_tracks` の応答に対し、最初の1回だけリスナー登録を行い、2回目以降の連続パケットは早期リターンします。
3. **ブラウザへの再生位置送信の間引き（100ms）**: 1秒に60回届く `/playing_position` を、サーバー側で各トラック 100ms（1秒間に10回）に間引いてブラウザに送信し、WebSocketの負荷を下げます。

## 2. 設計詳細

### 2.1 リクエスト再送制限と重複応答ガード
[packages/viewWaves/server.js](file:///c:/Users/watat/Documents/MySoftwares/AbletonOSC_Suite/packages/viewWaves/server.js)
- 送信管理変数 `lastNumTracksRequestTime = 0` を追加します。
- `setInterval` 内での `/live/song/get/num_tracks` 送信時、前回の送信から 2000ms（2秒）以上経過している場合のみ送信します。
- `/live/song/get/num_tracks` 受信時、すでに `numTracks > 0` であれば、`setupSongListeners()` の実行をスキップしてリターンします。

### 2.2 ブラウザへの再生位置送信の間引き（100ms）
- サーバー側で、最後にブラウザへ `clip_position` を送信した時刻を記録する `lastClipPositionEmitTime = {}`（Key: trackId, Value: timestamp）を導入します。
- `/live/clip/playing_position` 受信時、前回の `io.emit('clip_position')` 送信から 100ms 以上経過している場合のみ `io.emit` を実行します（これにより送信頻度を最大 10Hz に抑えます）。
- なお、Ableton からのパケットの受信および `lastAbletonMessageTime = Date.now()` や `activeClips[trackId] = slotIndex` の更新は**間引くことなく毎回実行**するため、疎通判定や再生中の状態管理には一切の影響（デグレ）はありません。

---

## 3. 影響範囲とリスク（デグレ防止）
- **ポーリング周期**: タイムアウト検知時間（4秒）はそのまま維持されるため、切断判定への影響はありません。
- **再生位置の追従精度**: ブラウザ側は `clip_position` を受信した際の基準時間から自前で線形補間（アニメーション）して滑らかに動かしているため、パケットの送信が 100ms 周期に間引かれても、カーソルの滑らかさや追従精度に影響（デグレ）は全くありません。
- **重複登録の回避**: `numTracks` が 0 の状態から 3 に確定した最初の1回だけ `setupSongListeners()` を実行するため、余分な OSC リクエストが発生しなくなり、Abletonの負荷を大幅に削減できます。

   - Ableton Live で曲を再生（1秒間に60発のパケットが飛んでいる状態）にします。
   - その状態でルーターを停止し（オレンジ明滅になり、画面がクリアされる）、再びルーターを起動します。
   - 通信復帰後、`server.log` を確認し、`/num_tracks` のバースト受信（20回連続）が起きても `setupSongListeners()` が1回のみ実行されること、および復帰した瞬間に即座に波形が表示されることを確認します。
